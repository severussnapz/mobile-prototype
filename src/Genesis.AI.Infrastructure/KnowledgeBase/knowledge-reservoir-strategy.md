# Executive Summary

EMIS Group holds a uniquely valuable knowledge asset: 25 years of clinical software development, regulatory compliance, and NHS operational experience encoded across codebases, product documentation, clinical safety records, customer interactions, and a proprietary Medical Knowledge Base. This knowledge has historically been siloed — accessible only to individuals with institutional memory, expensive to retrieve, and impossible to scale.

This strategy defines how EMIS transforms that asset into a structured, queryable Knowledge Reservoir — a persistent graph of institutional knowledge that compounds in value with every pipeline run, every support ticket resolved, and every capability built.

The Knowledge Reservoir has two primary applications: accelerating the Genesis AI SDLC pipeline across all 10 stages, and powering a broader set of high-value use cases including customer support, commercial responses, and strategic planning. The same investment in knowledge infrastructure delivers value across all applications simultaneously.

*The Knowledge Reservoir is not a search index. It is a structured graph that understands relationships — between requirements and code, between clinical hazards and mitigations, between customer problems and product decisions. That structural understanding is what makes it compounding and unreplicable.*

# The Knowledge Assets

EMIS holds seven categories of institutional knowledge that form the foundation of the Knowledge Reservoir. Each has a defined structure, extraction approach, and primary value contribution.

| **Knowledge Asset** | **Format** | **Primary Value** | **Extraction Approach** |
| --- | --- | --- | --- |
| Codebase (all repos) | Git repositories | Structural patterns, API contracts, implementation decisions | Graphify — AST extraction, zero LLM calls on source |
| Medical Knowledge Base (MKB) | Relational database (SQL) | Clinical domain ground truth — SNOMED, drug interactions, coding rules | Direct SQL ingestion → graph nodes with clinical ontology edges |
| Customer Support Tickets | Structured ticketing system | Failure history, resolution patterns, product gaps | API export → structured node ingestion with resolution edges |
| Clinical Hazard Logs | Excel (DCB0129 template) | Formally reviewed risk assessments and mitigations | Structured extraction → high-confidence graph nodes (already MHRA-reviewed) |
| User Guides | PDF / Word documents | Behavioural specification of what products actually do | Document extraction → Graphify semantic pass |
| Confluence / Design Docs | HTML / Markdown export | Architecture decisions, design rationale, NHS contracts | Confluence API export → Graphify document ingestion |
| Genesis AI Pipeline Artefacts | REQ files, parking lot, decisions | Forward-captured institutional knowledge with full provenance | Native — generated by the pipeline, immediately graph-ready |

Each asset contributes a different layer to the graph. The codebase provides structural truth — what exists. The MKB provides clinical truth — what is medically valid. Support tickets provide failure truth — what breaks. Hazard logs provide regulatory truth — what has been formally assessed. User guides provide behavioural truth — what users expect. Together they provide a ground truth that no generic AI system can replicate.

# Knowledge Graph Architecture

## Structural Layer — Graphify

Graphify handles the structural extraction layer. Installed as a skill across all EMIS repos and coding agents (Claude Code, Copilot, Cursor), it builds and maintains a queryable graph of code structure — call graphs, API endpoints, data models, dependency edges — updated automatically on every commit via git hooks.

Graphify natively ingests: source code (33 languages including C#, TypeScript, SQL, PowerShell), Markdown, PDFs, HTML, and JSON/YAML (including OpenAPI specs). Confluence pages exported as HTML and support ticket exports as Markdown feed directly into this layer with no additional tooling.

Every relationship is tagged EXTRACTED (from source), INFERRED (from LLM semantic pass), or AMBIGUOUS — ensuring the pipeline knows how much to trust each connection.

## Semantic Layer — Knowledge Graph Service

The Knowledge Graph Service (Plan KG, Darren Sheavills' team) adds the semantic enrichment that Graphify cannot derive from structure alone. This layer holds:

- Cross-capability relationships — Document Management depends on EMIS-X Auth v2.3 at commit abc123

- Requirements traceability — REQ-001 traces to hazard HAZ-DOC-002 traces to mitigation in auth service

- Version tracking — which pipeline stage was generated against which version of which artefact

- Clinical ontology edges — MKB concepts linked to codebase nodes and requirement nodes

- Failure provenance — support ticket resolution linked to the code change that fixed it

## Capability Catalogue

The Capability Catalogue is a structured registry of reusable EMIS-X capabilities and cross-cutting concerns. Each entry contains: capability ID, type (cross-cutting or domain), implementation status, links to OpenAPI specs, ADRs, and REQ files. Stored as structured Markdown, versioned in git, ingested by Graphify natively.

The catalogue is the mechanism that makes the Knowledge Reservoir actionable in the SDLC pipeline — it is the index that tells each pipeline stage what already exists and what can be referenced rather than rebuilt.

## Ingestion Strategy — Phased, Demand-Driven

The Knowledge Reservoir is not built in a single bulk exercise. 25 years of institutional knowledge cannot be manually curated at scale. The ingestion strategy is:

- Phase 1 — Structured data: codebase (Graphify), MKB (SQL ingestion), support tickets (API export), OpenAPI specs. High confidence, low effort, immediately useful. Weeks not months.

- Phase 2 — Document extraction: clinical hazard logs, user guides, Confluence export. Fed through Graphify's document extraction path on demand — triggered by pipeline needs, not as a bulk exercise.

- Phase 3 — Forward capture: every Genesis AI pipeline run adds nodes with full provenance. Within 12-18 months of pipeline operation, more structured institutional knowledge is captured than the preceding 25 years produced.

*The graph grows as the pipeline runs. The more capabilities built through Genesis AI, the richer the reservoir becomes — and the faster subsequent capabilities are built. This is the compounding effect.*

# Governance and Data Sovereignty

## Nothing Leaves the VPC

All knowledge reservoir infrastructure runs within the EMIS AWS VPC. Graphify's code extraction step performs AST parsing entirely on-device — no source code is transmitted to any external service. The semantic extraction step uses AWS Bedrock (IAM-authenticated, PrivateLink) — only semantic descriptions, never raw source code, are processed by the LLM. The MKB and clinical hazard log data never leave EMIS infrastructure.

## Clinical Data Handling

The Knowledge Reservoir contains no patient data. The MKB contains clinical knowledge (SNOMED codes, drug interaction rules, clinical workflows) not patient records. Support tickets and hazard logs are de-identified at ingestion. The graph contains institutional knowledge about how EMIS products handle clinical data — not the clinical data itself.

## Confidence Scoring

Every relationship in the graph is tagged with its confidence level: EXTRACTED (derived from source via deterministic AST parsing — highest confidence), INFERRED (derived via LLM semantic analysis — medium confidence, surfaced for human review), or AMBIGUOUS (conflicting signals — flagged, not used for generation without human confirmation). The pipeline never treats inferred relationships as ground truth.

## Version Tracking

Every pipeline stage that consumes a reference artefact records which version of that artefact it consumed — git commit hash for code and specs, document hash for PDFs and Excel files. When an artefact changes, the graph surfaces all pipeline stages and capabilities that were built against the previous version, enabling impact assessment before deployment.
